# STAY_SYNC_ARCHITECTURE.md

## Scope

This is a design document only. No schema or code changes are performed here.

## Verified repository facts

The repo has a real local-first Dexie database and optional cloud-sync architecture:
- `src/lib/db/index.ts` contains the Dexie schema and database instance.
- `src/lib/cloud/cloudContract.ts` defines the cloud contract and the set of tables that go to cloud storage.
- `db.use(cloudOutboxMiddleware)` registers a local outbox for cloud writes.
- `main.js` and `adminLink.js` show the desktop shell and its persisted admin control model.

This repo does not show a server-side accommodation booking engine or a full reservation lock service; instead, the app uses local-first state plus optional cloud syncing and per-device stored admin control.

## Existing sync pattern in the repo

The repo’s actual pattern is:
- local tables in Dexie
- an outbox / sync middleware for changed rows
- a centralized conversion layer in `cloudContract.ts`
- business-level, cloud document naming through `business_id`
- optional Firebase-backed sync for documents that match the app’s cloud contract

This pattern is not a full hotel booking transaction engine, so Stay should layer a stronger booking and financial safety model on top of it.

## How records are identified

Verified patterns in the repo:
- entity IDs are local UUID-like strings (`id` on each table) generated by the app and stored in Dexie.
- relationship boundaries are usually `business_id`.
- The cloud contract uses `business_id` and document IDs consistent with the local row keys.

For Stay, use:
- `id` as the natural row identifier for every record
- `business_id` for tenant scope
- `booking_id`, `stay_id`, `folio_id`, `invoice_id`, `payment_id` for cross-table relationships
- `sync_id` or `client_request_id` for mutation dedupe on network operations
- `version` or `updated_at` for optimistic concurrency

## How synchronization is triggered

The repo’s existing architecture triggers sync when data changes, not on a timer-only basis.

Observed pattern:
- Dexie writes trigger middleware.
- Changed records are queued for cloud syncing.
- The app’s cloud sync scheduler processes queued records.

For Stay, sync should remain event-driven and local-first. Proposed trigger rules:
- create/update/delete on bookings, stays, folios, payments, audit records, room states → enqueue sync
- room availability and rate changes → enqueue sync
- financial changes that affect ledger totals → enqueue sync
- night audit closure → enqueue sync after final state lock

### Safe queue semantics

Each queued mutation should include:
- entity type
- entity id
- business_id
- action (`create`, `update`, `delete`, `reconcile`, `refund`)
- payload hash
- `client_request_id`
- `created_at`
- `attempt_count`
- `last_error`

## Conflict resolution

Verified repo fact:
- The app uses a normalized cloud contract and field mapping, but the code does not show a full reservation conflict lock or multi-writer coordination layer.

For Stay, the conflict model must be stricter:

### Non-financial operational records
- Use last-write-wins only when the entity is naturally single-writer and not a reservation or financial ledger.
- Example: housekeeping task status update or room maintenance note.

### Reservation and occupancy records
- Use optimistic concurrency with version checks.
- If two devices attempt to book the same room for overlapping dates, only one can commit the final reservation state.
- Prefer a per-room availability check + lock at the business scope before final booking confirmation.

### Payment and folio entries
- Never apply a later payment without a ledger validation against the current folio state.
- If conflicting payment entries exist, the system should mark the later one as `needs_review` or `duplicate_detected` rather than silently overwriting.

### Night audit
- Night audit must be a serial event: one open session at a time per business day.
- A second session cannot close the same day unless the first is reconciled or reopened.

## Failed operations and retries

The repo does not show a full retry / idempotency framework beyond local outbox and general sync processing. For Stay we must enforce stronger semantics.

Recommended approach:
- each cloud mutation is retried with exponential backoff
- operations are idempotent using a stable `client_request_id`
- if a payment or booking record is already committed, a retry must map to the same logical operation and not create a duplicate
- failed syncs remain in the local outbox with status `pending`, `retrying`, `failed`, `stuck`

### Payment safety

Payment submissions must be idempotent by:
- `stay_id`
- `payment_method`
- `amount_paise`
- `reference_number`
- `client_request_id`

If the same payment is retried, the system should return the same payment record instead of creating a second payment.

## Duplicate prevention

Specific Stay risks:
1. Duplicate booking creation while offline
2. Duplicate check-in on same room
3. Duplicate payment submission when connectivity returns
4. Duplicate audit closure during offline reconnection

Recommended protection:
- `reservation_token` created at the time the booking is drafted
- `stay_id` / `booking_id` locked by a unique repository-level claim check
- `payment idempotency key` required before posting a payment
- `night_audit_session` unique lock by `business_id + business_day`
- `stay_entered_at` and `room_id` uniqueness on active stays

## Local migrations and restoration

The repo does use Dexie versioned migrations in `src/lib/db/index.ts`.

Stay must use the same pattern but with stricter migration safeguards:
- no destructive migration for financial state
- any migration affecting folios, payments or audit sessions must be backward compatible
- each migration should include a checksum or data validation step
- on app restart, the database should restore queued sync mutations from outbox before reprocessing

### Recovery after restart

Design requirement:
- the app reloads local queue state from Dexie
- unsent sync rows are retried automatically
- if a room booking was created but cloud sync failed, the local record remains with `sync_status = pending`
- if the device restarts mid-check-in, the system rehydrates from local unsynced state rather than creating duplicate stays

## Concurrent multi-device behavior

The repo supports local-first multi-device patterns and cloud-synced data, but no explicit cross-device reservation lock is shown.

For Stay, the safe model is:
- the reservation and check-in flow must acquire a room availability reservation token
- conflicts are detected in the chosen transaction boundary before final confirmation
- multi-device updates are supported only with a clear serializable conflict policy around room state and folio posting

### Required guardrails

- `bookings` cannot be confirmed if the room is already marked occupied by a different active stay
- `check_in` cannot succeed if a stay exists for that room and date range
- a second payment with the same idempotency key cannot be posted twice
- a second night audit session cannot close the same date while the previous one is open

## Safe synchronization approach for Stay

### Recommended approach

Use the existing Dexie + local outbox model, but augment it with a service-layer lock and idempotency model.

Core rules:
1. Local state is the source of truth while offline.
2. All financial writes must be validated against the current local ledger state before sync.
3. The cloud is a replication layer, not a broker of booking truth for final cancellation or payment posting.
4. A device may accept an offline booking, but cannot safely confirm the hold or sale if it cannot validate room availability or the business is disabled.

### Operation-specific safety

#### Simultaneous room booking
- Not safe to confirm without a reservation lock / room availability check.
- The app should accept “pending booking request” locally and resolve to one winner when connectivity returns.

#### Simultaneous check-in
- Not safe to confirm offline.
- The app may allow a local draft or provisional check-in but must require room availability validation before finalization.

#### Duplicate payment submissions
- Not safe to confirm if no idempotency key or duplicate detector exists.
- All payments should be posted only once with one stable idempotency key.

#### Offline booking creation
- Allowed as local draft or provisional booking.
- It remains in `pending_sync` status until the room is reserved in the authoritative state.

#### Night audit during connectivity loss
- Allowed to record local audit drafts and cash variances.
- Final closure should only be committed when the business day and ledger are stable and the local session is re-synced.

#### Admin disabling Stay while devices are offline
- The app must keep the last admin control state locally.
- The next successful sync or app restart should apply the disabled state.
- Local UI must not continue to show room data or allow booking actions after the disable flag is present.

## Operations that cannot safely be confirmed offline

These should be explicitly blocked or treated as provisional only:
- final room booking confirmation for a currently occupied room
- final check-in against a room already assigned to another active stay
- payment posting for room charges and deposits
- invoice issuance and final settlement
- night audit close
- refund processing that alters the financial ledger
- any operation that changes the room occupancy state with real financial effect

These operations may still be drafted locally but should carry `provisional` status until online validation succeeds.

## Recommendation summary

- Keep the repo’s Dexie + outbox pattern.
- Add `client_request_id`, idempotency checks, and room-level reservation locks.
- Treat all accommodation financial writes as ledger-posting transactions, not as simple CRUD writes.
- Make admin disablement part of the sync contract, not just a UI toggle.
- Keep the official booking truth at the business layer, not on an individual device.

## Finalized offline and synchronization policy (2026-11-16)

### Classification

A. Safe to complete offline
- local booking draft creation
- local room state draft notes
- local housekeeping task updates pending sync
- local cleaning status change with operational note
- local audit draft capture if not yet finalized

B. Allowed as provisional offline operation
- tentative room hold
- provisional booking request
- provisional check-in draft
- local payment draft with no final ledger posting
- local refund draft without final approval

C. Must be validated online before final confirmation
- confirmed booking with room allocation
- check-in completion against a room with active occupancy
- final payment posting to a folio
- refund processing and ledger reversal
- invoice issuance and invoice correction
- night audit close and daily reconciliation

### Reason
These categories reflect the real constraints of a local-first app: local state is safe for draft and queueing, but room allocation, financial posting and audit closure require authoritative validation to prevent double booking or duplicate accounting.

### Alternatives considered
- Allow everything offline: rejected because it creates duplicate booking, double payment and audit risk.
- Treat all offline actions as final immediately: rejected because room allocation and financial posting cannot be safely confirmed without validation.

### Risks
- provisional booking may later be rejected
- offline payment may be re-queued and double-submitted if idempotency is weak
- open audit session may close incorrectly if multiple devices participate

### Testing implications
- test offline draft persistence and resync
- test duplicate payment rejection using idempotency keys
- test final confirmation rejection when room is already occupied
- test night audit close while offline remains provisional until validation

### Idempotency and retry design
- each financial mutation must carry a stable `client_request_id`
- retry of the same mutation must resolve to the same logical result
- payments must reject duplicates using `stay_id + payer_id + amount + payment_method + reference_number + client_request_id`
- bookings must reject duplicate reservation tokens for the same room/date window
- audit closures must be unique per `business_id + business_day`

### Authoritative service boundary
The multi-device room allocation boundary must be a serialized or centrally coordinated reservation service at business scope. Dexie + outbox alone is sufficient for queueing, but not for authoritative room commitment when multiple devices race.

## Unresolved decisions

- Whether the business-level reservation lock is enforced by a cloud service or by a strictly serialized local queue for single-device desktop deployments.
- Whether mobile clients should be allowed to create provisional bookings offline or whether they must wait for connectivity.
- Whether the app should record each payment as a single ledger row or split it into payment, allocation and invoice lines at the first transaction boundary.
